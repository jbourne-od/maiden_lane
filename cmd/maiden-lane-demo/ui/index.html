What you are looking at

Two truck drivers are reporting hours-of-service observations. The task is to combine them into one team HOS record. That is only meaningful if the two reports actually describe the same thing — the same assignment, the same duty period, internally consistent hours. When they do not, the honest output is not an average. It is a refusal.

  1. A declared program, not code. The rules, checkpoints, and completeness profiles are declarations. The compiler turns them into a plan whose identity is derived from its content, so the same program always has the same name.
  2. A pinned observation. The input is fixed and identified by content too. A different observation is a different run, never the same run with different data.
  3. Transitions commit one at a time. Each rule either commits or is refused. At declared boundaries the engine seals a checkpoint: an immutable, replay-verified record of everything accepted so far.
  4. Refusal is specific and keeps what was earned. A refused boundary names a closed code. Checkpoints sealed before it stay sealed.
  5. Readiness is asked per consumer. The same sealed checkpoint can be complete enough to publish to one system and not another. Both answers are real answers.

Everything on this page comes from the documented HTTP API. Open your browser's network tab — the requests you will see are POST /v1/plans, POST /v1/executions, and GET /v1/executions/{id}. Nothing is precomputed and there is no demo path through the engine.
