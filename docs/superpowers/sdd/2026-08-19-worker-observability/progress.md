# SDD ledger — worker observability (no separate plan document; scope agreed in conversation)
Setup: branch `claude/worker-observability` off `main` at f68bf70 (PR #12 and #13 merged); baseline `make verify` passed. Scope agreed with the owner as "the minimal version": a worker span so worker-driven executions have a trace root, trace-correlated logs on top of it, and the worker outcome metrics that were previously absent. Explicitly out of scope: carrying the submission's trace context through the queue to link the 202 to the work, which is a durable-storage decision.
Motivating defect, observed rather than predicted: PR #13's stack was used to read a worker-driven execution's trace, and one logical execution produced four traces — `POST /v1/plans`, `POST /v1/executions` (the 202 alone), a rootless 10-span trace containing the actual work, and `GET /v1/executions/{id}`. Spans attach to whatever is in the context they are given and `app.Observer` is forbidden from replacing the context, so an execution driven over HTTP nests under the request span while one driven by the worker had nothing above it.
Prediction partially refuted before building: I expected the run to fragment internally as well, with `compile` becoming a second root. It did not. `app.Run` maintains parentage correctly, so the break was only at the queue boundary. Worth recording because it changed the fix from "repair parentage inside the run" to "give the worker a root", which is much smaller.
Severity revised down by measurement: correlation was already possible, because the spine's phase spans carry `maiden_lane.semantic.execution_id`, so `{ span.maiden_lane.semantic.execution_id = "..." }` found the orphaned work from the identity the API returned. The defect was no click-through and no root, not an inability to correlate. Recorded because it argued for the minimal fix rather than the schema change.
Task 1 — worker span: complete. `worker.ExecutionTracer` is a consumer-owned interface in the worker package, implemented in internal/observability, following the precedent of `app.Observer`. Unlike `app.Observer` it RETURNS a context, and that is its whole purpose: the returned context is what parents the spine's phases. A nil tracer is supported and behaves exactly as before.
Task 1 decision — the span reuses the spine's identity attribute names (`maiden_lane.semantic.plan_id`, `.run_id`, `.execution_id`) rather than inventing worker-scoped ones, so one TraceQL predicate matches the worker span and every phase beneath it. Verified live: the predicate matches 10 of 11 spans. The one that does not is `compile`, which legitimately has no execution identity because none exists until the run is bound.
Task 1 decision — span kind is Consumer, and the span is deliberately NOT a child of the submission that queued it. It cannot be: that request finished long before and its span with it. Linking them needs the submission's trace context carried through the queue, which means a column on `executions` that must be excluded from the identity hash, plus an answer to what happens on idempotent resubmission — the stored context belongs to the FIRST submission, so a later submitter could never link. Deferred deliberately rather than half-built.
Task 1 decision — no tenant on the span. The spine's spans carry none, and widening that is a privacy decision rather than a plumbing one.
Task 1 refactor, needed for correctness rather than tidiness: `process` split into `process` (opens the span, closes it with the outcome) and `attempt` (the body, returning an outcome at every exit). The recover defer sets the named return, so it runs BEFORE the span closes and a panicking execution reports a terminal failure instead of a zero value. Registering the two defers the other way round would have closed the span with whatever the last assignment happened to be.
Task 1 improvement the outcome forced: `fail` and `recordInability` now RETURN what they recorded rather than only doing it. That surfaced a distinction the code previously blurred — an intended terminal failure that could not be written leaves the execution claimable, so it reports `abandoned`, not `failed`. Reporting `failed` would describe a state no reader can observe. Two contract-style assertions cover exactly those two cases.
Task 1 vocabulary decision: the bounded failure reasons moved from unexported constants in worker.go to exported ones in tracing.go, because `ExecutionOutcome.Reason` is part of the package surface and a bounded field whose permitted values cannot be named outside the package is bounded in comment only.
Task 2 — trace-correlated logs: complete. `NewLogger` now wraps its JSON handler with `traceContextHandler`, which adds `trace_id` and `span_id` when the context carries a valid span context. Records logged through the non-Context variants carry neither, which is correct: process lifecycle logging happens outside any span, and a startup line claiming to belong to a trace would be worse than one that stays silent. Verified live — all four startup lines carry no trace identity.
Task 2 finding that corrected my own earlier claim: I told the owner this needed 43 call sites converted. The real number is 12, and that grep had counted `err.Error()` string calls, generated code, and plan markdown. More importantly, NONE of the 12 sits inside a span: nine are process lifecycle in main.go and three are internal error sinks, one of which is an `io.Writer` the stdlib hands no context at all. The blocker was never call-site plumbing — it was that no log statement existed inside an active span, which is exactly what Task 1 changed. The worker's five error-path sites now use the Context variants and are the only ones that can correlate.
Task 2 correctness detail: the handler clones the Record before adding attributes, because slog Records share attribute backing storage with their copies. `TestAddingTraceIdentityDoesNotLeakBetweenRecords` asserts a second record does not inherit the first's trace identity — the failure a missing clone actually produces.
Task 2 limitation, stated rather than hidden: the positive path is covered by unit tests, not by the live run. Every worker log site is an error path and none is reachable from the API in a local process without tampering, so a live positive demonstration was not obtained. The live run confirms only the negative case.
Task 3 — worker metrics: complete. `maiden_lane.execution.outcomes` (counter, `result` and optional `failure_reason`) and `maiden_lane.execution.duration` (histogram, `result`). Both are recorded by the same adapter call that closes the span, from the SAME outcome value, so a trace and a graph cannot disagree about one execution. No new worker surface was needed — the tracer already received the outcome.
Task 3 decision applying PR #13's finding: the counter declares its unit as the braced annotation `{execution}` rather than `executions`. Unlike the four semantic counters, this name does not end in its own unit word, so an unbraced unit would have produced `maiden_lane_execution_outcomes_executions_total`. Verified by reading the series back: `maiden_lane_execution_outcomes_total`. METRICS.md now names this as the case new counters should follow, since the semantic counters' clean names depend on a coincidence.
Task 3 decision also applying #13's finding: the duration histogram declares explicit boundaries (5 ms to 60 s) rather than inheriting the SDK's millisecond-shaped defaults. A test asserts the histogram has boundaries at all, because an unset aggregation is exactly how the previous defect happened.
Task 3 INCONSISTENCY I introduced and then fixed: I first used one set of constants for both the span attributes and the metric dimensions, which published `maiden_lane_execution_result` as a Prometheus label on a series already called `maiden_lane_execution_outcomes`. The repository deliberately separates the two — span attributes are prefixed because a span accumulates attributes from every layer it passes through, while a metric dimension is already scoped by its instrument, which is why the ratified semantic dimensions are bare `phase` and `result`. Split into `attribute*` and `dimension*` constants, with a test pinning that the prefixed names never reach a metric dimension. Caught by reading the live label set, not by any test I had written.
Task 3 fail-closed behaviour, following the ratified optional-dimension rule: an unadmitted outcome kind records NO metric point and no label, while an unadmitted failure reason still counts the failure but omits the dimension — the execution did fail, and dropping the point over a labelling problem would understate failures. Both asserted.
Task 3 structural change: metric views are now assembled in one `allMetricViews`, so adding an instrument family without its attribute allowlist is a visible omission rather than a silent one.
Worker metrics NOT added, and why: lease expiry and reclaim counts are the two an operator most wants and neither is observable from the worker. A reclaim happens inside the store, when a claim selects a row whose lease lapsed; metering it means instrumenting the adapters, which currently take no observer at all. That is a real design decision about whether ports grow an observation seam, not an oversight to fold in here.
Verification: `make verify` clean, `-race` clean on the changed packages, and a live three-signal check against the stack from PR #13 — the worker span roots an 11-span trace with `execute_spine` and all nine phases beneath it, the counter and histogram arrive in Prometheus under the documented names with the documented dimensions, and startup logs correctly carry no trace identity.
Repository note for the owner, no change made: the Makefile still prunes `-name .superpowers`, which no longer exists after the move to docs/superpowers. It is dead rather than harmful — the moved files are Markdown, which gofmt never visits.
