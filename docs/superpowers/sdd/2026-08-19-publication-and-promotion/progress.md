The argument that decided it is least privilege. A binary that applies its own migrations needs a runtime role with DDL rights, which means the process serving requests can ALTER or DROP the tables holding sealed artifacts. For a system whose proposition is that its record lineage is immutable and attributable, that is the one place a structural guarantee would be replaced by trust — the same reasoning already enforced by "storage cannot lie about identity" rather than being relied on not to. Supporting reasons, in descending weight: a long migration or backfill does not belong in a starting process, where an advisory lock makes N−1 tasks wait and a slow index build can outlast a health-check grace period; migration and deploy stay separately reversible, so rolling a binary back does not leave the schema ahead of the code; plain SQL is reviewable by contributors who do not read Go.
The standard objection to a separate step — someone forgets it — is answered by the pattern already in use here: the binary refuses to start, exactly as an unreachable configured database already blocks startup rather than degrading to memory.

Slice 1 decision — the migration files are embedded to be READ, never applied. Slice 2 ARCHITECTURE FINDING that decided where this lives: HLD §6 enumerates every derived identity in the system — InputID, PlanID, SemanticRunID, ExecutionID, ProfileID, CheckpointArtifactID, AssessmentID — and a target policy is NOT among them. §14.1 correspondingly says a publication record pins the policy *version*. So a policy is control-plane configuration naming which semantic contract a destination demands, not a semantic artifact. The kernel is therefore untouched again: no new artifact type, no new canonical encoder, no change to internal/semantic. Had I assumed content-addressing by symmetry with everything else here, I would have added a kernel artifact the ratified identity model does not have.
Slice 2 decision — the policy binds exactly one thing, the required ProfileID, because that is what §14.1 asks of it. The three unreachable gate clauses will need fields here and each will arrive with a migration when the concept it refers to exists. Adding them now would be inventing a shape for a decision nobody has made.
Slice 2 decision — RequiredProfileID rather than a profile key. A key is a name an author chose and can reuse; a ProfileID identifies one specific compiled contract. Binding the key would let the requirement change underneath a publication that had already been authorized by it.
Slice 2 decision — writing a policy is a compare-and-swap: the supplied version must be exactly one greater than the current one. The store does NOT allocate the next version. Two operators editing one target concurrently is the case this exists for, and for an audit-bearing rule, the loser learning it lost matters more than the convenience of not having to read first. Identical content under a recorded version succeeds so a retry is safe; different content under a recorded version is a conflict, because that is an attempt to rewrite what an existing publication pinned.
Slice 2 decision — version zero is refused rather than treated as absent, so "no policy" and "policy version zero" are not two states every reader must distinguish. Enforced in both adapters and by a CHECK constraint, so a direct SQL write cannot introduce what application code refuses.
Slice 2 Postgres implementation: the succession check and the insert are ONE statement, an INSERT ... SELECT whose WHERE compares the supplied version against `1 + COALESCE(max(version), 0)`. A source yielding no row inserts nothing, which expresses "your version does not follow the current one" without a transaction or a caller-held lock. The primary key handles the rest: a concurrent writer with the same version loses to a unique violation rather than overwriting, so immutability holds at the database and not only in application code. The concurrency assertion passing against a real database is what establishes that, and it also exercises the SQLSTATE match — a wrong code would surface a raw write error instead of ErrPolicyConflict and fail the assertion.

Slice 3 (the gate), part one: complete. internal/promotion declares the result model with the structural guarantees, and the clause evaluation is deliberately not written yet — see the finding below.
Slice 3 decision, from owner review — not_evaluated and not_satisfied must stay distinguishable. Both refuse, but only one says something adverse about the candidate. HLD §14 already ratifies three verdicts, so `fail` IS not_satisfied and no new verdict was needed. The owner's sketch also implied a further distinction between "unsupported" and "not evaluated", which is real: one is answered by implementing something, the other by supplying something. Rather than add a fourth verdict and deviate from a ratified enum, Unevaluated is a separate axis meaningful only when the verdict is NotEvaluated — the same {Kind, Reason} shape the worker outcome already uses.
Slice 3 decision — NotEvaluated is the ZERO VALUE of Verdict, and this is the load-bearing decision in the package. A clause nobody filled in, a struct a future caller builds without a field, an empty slice: all yield NotEvaluated, which refuses. Authorization cannot be obtained by omission, only by an explicit Pass on every required clause. Ordering the constants any other way would still compile, still pass every other test, and would authorize publication on an empty decision. Probed: reordering so Pass is zero fails exactly one test, TestTheZeroVerdictRefuses, which is precisely why that assertion earns its place — decide() writes NotEvaluated explicitly for absent clauses, so nothing else covers the ordering.
Slice 3 decision — the overall verdict is computed by walking the closed clause list, NOT the verdicts a caller supplied. Walking the supplied set would authorize a caller who evaluated one clause and passed it, because everything it checked passed. Asserted directly.
Slice 3 decision — the decision carries the policy version, so two questions are answerable independently: which semantic facts produced this result, and under which destination policy was it judged. The version participates in no semantic identity and never reaches the kernel, which is the boundary Slice 2 established.
Slice 3 FINDING that stopped clause evaluation, and the reason it is a question rather than a guess: clause 3 requires that all protected dynamic invariants applicable to the checkpoint prefix passed, and that is NOT verifiable from what exists. CheckpointArtifact exposes only InvariantResultDigest() — the digest of the results, not the results — and ports.SealedCheckpoint does not retain []InvariantResult at all. So for any execution read back from storage there is no evidence to evaluate the clause against.
Three ways forward, with a recommendation rather than a choice made unilaterally. (a) Infer it from sealing, since the spine structurally cannot seal a checkpoint whose protected invariants failed. Defensible and against the grain of everything else here: the gate would assert a clause it did not check, which is the same shape as trusting storage rather than re-deriving. (b) Persist []InvariantResult so the gate verifies them against the pinned digest — real work (migration, codec, contract assertions) and it makes clauses 3 and 8 mutually reinforcing, since checking the supplied results hash to the pinned digest is exactly clause 8. (c) Report clause 3 as NotEvaluated / InformationAbsent until (b) lands. Recommended interim: it costs nothing in demoability, because the blocking decision already means the gate publishes nothing, and it keeps the gate from ever claiming a clause it did not evaluate. Note this is precisely the distinction the owner predicted would matter immediately in Slice 3.
