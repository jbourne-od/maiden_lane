The argument that decided it is least privilege. A binary that applies its own migrations needs a runtime role with DDL rights, which means the process serving requests can ALTER or DROP the tables holding sealed artifacts. For a system whose proposition is that its record lineage is immutable and attributable, that is the one place a structural guarantee would be replaced by trust — the same reasoning already enforced by "storage cannot lie about identity" rather than being relied on not to. Supporting reasons, in descending weight: a long migration or backfill does not belong in a starting process, where an advisory lock makes N−1 tasks wait and a slow index build can outlast a health-check grace period; migration and deploy stay separately reversible, so rolling a binary back does not leave the schema ahead of the code; plain SQL is reviewable by contributors who do not read Go.
The standard objection to a separate step — someone forgets it — is answered by the pattern already in use here: the binary refuses to start, exactly as an unreachable configured database already blocks startup rather than degrading to memory.

Slice 2 decision — writing a policy is a compare-and-swap: the supplied version must be exactly one greater than the current one. The store does NOT allocate the next version. Two operators editing one target concurrently is the case this exists for, and for an audit-bearing rule, the loser learning it lost matters more than the convenience of not having to read first. Identical content under a recorded version succeeds so a retry is safe; different content under a recorded version is a conflict, because that is an attempt to rewrite what an existing publication pinned.
Slice 2 decision — version zero is refused rather than treated as absent, so "no policy" and "policy version zero" are not two states every reader must distinguish. Enforced in both adapters and by a CHECK constraint, so a direct SQL write cannot introduce what application code refuses.
Slice 2 Postgres implementation: the succession check and the insert are ONE statement, an INSERT ... SELECT whose WHERE compares the supplied version against `1 + COALESCE(max(version), 0)`. A source yielding no row inserts nothing, which expresses "your version does not follow the current one" without a transaction or a caller-held lock. The primary key handles the rest: a concurrent writer with the same version loses to a unique violation rather than overwriting, so immutability holds at the database and not only in application code. The concurrency assertion passing against a real database is what establishes that, and it also exercises the SQLSTATE match — a wrong code would surface a raw write error instead of ErrPolicyConflict and fail the assertion.
