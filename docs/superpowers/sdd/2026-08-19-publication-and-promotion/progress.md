The argument that decided it is least privilege. A binary that applies its own migrations needs a runtime role with DDL rights, which means the process serving requests can ALTER or DROP the tables holding sealed artifacts. For a system whose proposition is that its record lineage is immutable and attributable, that is the one place a structural guarantee would be replaced by trust — the same reasoning already enforced by "storage cannot lie about identity" rather than being relied on not to. Supporting reasons, in descending weight: a long migration or backfill does not belong in a starting process, where an advisory lock makes N−1 tasks wait and a slow index build can outlast a health-check grace period; migration and deploy stay separately reversible, so rolling a binary back does not leave the schema ahead of the code; plain SQL is reviewable by contributors who do not read Go.
The standard objection to a separate step — someone forgets it — is answered by the pattern already in use here: the binary refuses to start, exactly as an unreachable configured database already blocks startup rather than degrading to memory.

Slice 2 decision — RequiredProfileID rather than a profile key. A key is a name an author chose and can reuse; a ProfileID identifies one specific compiled contract. Binding the key would let the requirement change underneath a publication that had already been authorized by it.
Slice 2 decision — writing a policy is a compare-and-swap: the supplied version must be exactly one greater than the current one. The store does NOT allocate the next version. Two operators editing one target concurrently is the case this exists for, and for an audit-bearing rule, the loser learning it lost matters more than the convenience of not having to read first. Identical content under a recorded version succeeds so a retry is safe; different content under a recorded version is a conflict, because that is an attempt to rewrite what an existing publication pinned.
Slice 2 decision — version zero is refused rather than treated as absent, so "no policy" and "policy version zero" are not two states every reader must distinguish. Enforced in both adapters and by a CHECK constraint, so a direct SQL write cannot introduce what application code refuses.
Slice 2 Postgres implementation: the succession check and the insert are ONE statement, an INSERT ... SELECT whose WHERE compares the supplied version against `1 + COALESCE(max(version), 0)`. A source yielding no row inserts nothing, which expresses "your version does not follow the current one" without a transaction or a caller-held lock. The primary key handles the rest: a concurrent writer with the same version loses to a unique violation rather than overwriting, so immutability holds at the database and not only in application code. The concurrency assertion passing against a real database is what establishes that, and it also exercises the SQLSTATE match — a wrong code would surface a raw write error instead of ErrPolicyConflict and fail the assertion.

Slice 4, publication: complete. The versioned pointer, its compare-and-swap, both adapters, the shared contract suite, and the application use case that evaluates the gate and refuses. It ships able to publish nothing, which is asserted rather than assumed.
DESIGN: append-only publication records keyed (tenant, customer, target, version), not a mutable row. §14.1 calls publication "a compare-and-swap update of a versioned pointer", and history satisfies that while also keeping every superseded publication readable. That is what makes an old decision explainable, and it is also why PublicationStatus is NOT stored: HLD §14 ratifies unpublished/published/superseded, and all three are derivable — no record, the highest version, any lower version. A status column would be a fourth thing able to disagree with the first three, with no resolution available. Recorded here because not modelling a ratified vocabulary looks like an omission and is not one.
DESIGN: the record pins the six things §14.1 names and stores NO gate verdict. The verdict is reproducible from the pinned identities because gate evaluation is pure, so storing it would add a projection able to disagree with the artifacts it summarizes — and a disagreement there is unresolvable, since nothing could say whether the artifacts changed meaning or the summary was wrong when written. Same reasoning as the owner's correction in (b): pin the inputs, re-derive the answer.
DESIGN: no PlanID column. SemanticRunID is derived from the plan together with the input, world, and provenance policy, so the plan is already committed to by the run the record names. A column would be a second statement of one fact, able to drift.
FINDING that changed the request type: a CheckpointArtifact carries NO execution identity, deliberately — executor identity affects only ExecutionID, so one semantic run can be executed more than once and produce the same checkpoint. So the execution cannot be authenticated from the checkpoint, and a bare ExecutionID parameter would let a record name an execution that did not produce the artifact beside it: complete-looking, and auditing to a contradiction. PublishRequest therefore takes a semantic.RunBinding, which only BindRun produces and which commits to SemanticRunID and ExecutionID together, plus a check that the binding's run is the checkpoint's.
The mismatch is an ERROR, not a gate refusal, because it says nothing about the candidate — it says the request cannot produce a truthful record. Both new failures use the package's existing InvalidInputError with closed codes, PUBLISH_REQUEST_INCOMPLETE and PUBLISH_BINDING_MISMATCH. Two codes rather than one for the same reason the gate has two unevaluated reasons: one is answered by supplying a missing piece, the other by correcting a pairing that is complete and wrong.
MY FIRST DRAFT VIOLATED THIS PACKAGE'S OWN CONVENTION: the mismatch error interpolated the semantic run and checkpoint identities into its text, while InvalidInputError is documented as fixed safe text where "no payload, identifier, path, or raw dependency text ever appears". Fixed, and asserted by a test that the identity does not appear in the message.
An absent policy needs no special case: the zero TargetPolicy is handed to the gate, which reports every clause unevaluated for want of a policy. That is the truthful answer and better than a bespoke error, because an unconfigured target is an ordinary state rather than a fault.
IDEMPOTENCE ON REPUBLICATION, and this is the normal case rather than an edge case: execution delivery is at-least-once by design because a lease can expire and a second attempt reproduces byte-identical artifacts. Re-publishing exactly what is already current therefore appends nothing. Without it an expired lease would leave a target's history showing the same checkpoint published twice, and nothing later could distinguish that from two real decisions. The comparison ignores the version and nothing else: the version distinguishes two records, the pinned identities distinguish two decisions.
COVERAGE PROBLEM FACED RATHER THAN PAPERED OVER: with the gate refusing everything, Publish's authorize-and-advance path is unreachable from outside the package. The seam that would fix it — an injected gate function — is refused, because it would let any caller hand Publish an authorization it did not compute, which is the hole this whole design avoids. So samePublication and publicationFor have direct in-package unit tests instead. Untested code that becomes load-bearing the instant a clause is wired is the worse trade.

OWNER REVIEW of #22 found TWO CORRECTNESS BLOCKERS, both accepted, both at the application boundary rather than in the adapters. Storage design, the seam refusal, the status/verdict derivation decisions, and the refusal-only gate were left alone.
BLOCKER 1, and the spec says it outright: HLD §16 line 729 requires publication to take "the expected current target version". My Publish read whatever was current and wrote one past it. That protects only the window between the internal read and the write, and not the window that matters, which opens when the caller DECIDES and closes when it publishes. If A publishes v7 after B formed its decision against v6, B observes v7 and writes v8 over a result it never saw — a flawless compare-and-swap on the wrong proposition. Fixed by PublishRequest.ExpectedCurrentVersion, so the record is written at expected+1 and a caller whose token does not match loses. Verified non-vacuous by reintroducing the defect: both new tests fail against it and pass with the fix.
The ordering inside advancePointer is load-bearing and now documented: the already-published check must come BEFORE the expected-version check. An at-least-once retry re-derives the same decision from the same expected version, and by then its own earlier publication is current, so checking the version first would refuse an idempotent retry as stale — a conflict the caller cannot resolve, because its view is not wrong, it is already satisfied.
Recorded honestly rather than claimed as fixed: a retry whose policy advanced in the meantime is NOT recognised as a retry, because its record pins the new policy version. The token guarantees only that such a retry cannot advance history from a version it did not name. Whether it SHOULD republish under a new policy is a real question this slice does not answer. A test asserts the non-silence, not a resolution.
BLOCKER 2, and the owner's reasoning was sharper than mine: RunBinding does not establish what I claimed. BindRun happens BEFORE execution and proves only that an ExecutionID is a valid execution contract for a SemanticRunID. CheckpointArtifact excludes producing-executor identity by design, so it carries SemanticRunID and not ExecutionID. Holding a binding whose run matches a checkpoint's therefore proves E → S ← C, which is strictly weaker than E → C.
PROVED EMPIRICALLY BEFORE FIXING, with a throwaway probe: bind a second executor over the identical semantic request (same SemanticRunID, different ExecutionID), never execute it, pair it with a checkpoint another execution really produced, and validatePublishRequest accepted it. The record would have named an execution that did not produce the artifact beside it. My test could not have caught this because it used a binding from a different SEMANTIC RUN, which changes the identity the check compares.
Fixed the owner's way, and it needs no ExecutionID on CheckpointArtifact: SpineResult mints an opaque app-level CheckpointReceipt of (ExecutionID, SemanticRunID, CheckpointArtifactID), and only when that checkpoint is among the ones the run actually retained. Its fields are unexported and ReceiptFor is the only constructor, so a caller cannot assemble one — verified by compiling an attempted forgery from an external test package and confirming the compiler refuses it.
A property worth stating: if a second executor DID run and produce the same checkpoint, its receipt is honest, because it really did produce it. The receipt rules out attribution to an execution that never happened, which is exactly the claim at issue, rather than ruling out multiple honest producers.
Retention matters too, not just membership. A checkpoint can be sealed and then excluded from the frontier when its assessment fails verification, so ReceiptFor requires the checkpoint to be RETAINED; publishing an excluded one would publish an artifact the run deliberately did not stand behind.
Validation now checks the receipt is for THIS checkpoint. Without it, a receipt for one retained checkpoint could be paired with another's artifact — both genuinely from the execution, so the receipt is honest and simply for the wrong one. The run comparison is kept as well, and is now redundant against a correct receipt: it guards a minting defect rather than a caller. Code InputPublishBindingMismatch became InputPublishReceiptMismatch.
BLOCKER 3, test strength: my publicationFor test used a zero candidate and asserted none of AssessmentID, CheckpointArtifactID, SemanticRunID, or ExecutionID, while the behavioural test hand-built a ports.Publication instead of calling publicationFor. All four load-bearing mappings could have been swapped or dropped unnoticed. Now compared field-for-field against real spine artifacts, plus assertions that the sources are genuinely distinguishable so a helper reading the wrong one cannot be coincidentally right.
The publish tests moved into package app so ONE real spine fixture serves both the behavioural and the direct tests. The fixture now runs the real spine rather than driving the kernel, which it must: a receipt can only be minted by a SpineResult, and a fixture that assembled one another way would test a construction production cannot perform.
advancePointer was extracted so the four compare-and-swap outcomes are directly testable — recorded, unchanged, stale conflict, store conflict — all of which sit past authorization and were therefore unreachable.
