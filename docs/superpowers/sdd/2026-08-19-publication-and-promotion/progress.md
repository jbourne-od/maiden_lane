Planning finding that shaped the whole programme: HLD §14.1 defines a ten-clause promotion gate and three clauses are unreachable today — baseline-versus-candidate execution over the same replay corpus, no protected metric regression, and a backend certified against the reference executor. None of those concepts exists in the codebase (`grep` for Corpus, Regression, Certif returned essentially nothing). Seven of ten are reachable because every identity, sealed artifact, and assessment they need is already stored. Recording this before building, because "promotion" is otherwise a name that could ship covering seven clauses while reading as ten.
Owner decision ratified 2026-08-19: an unevaluated protected gate clause BLOCKS publication. The three unreachable clauses will record `not_evaluated` and refuse. Chosen over a structurally distinct provisional publication kind, and over non-blocking `not_evaluated`. Stated consequence the owner accepted: nothing publishes until comparison, regression, and certification exist, so the publishing demo moves behind three more slices.
Owner decision ratified 2026-08-19, SUPERSEDING an earlier one in the same session: migrations use dbmate as an explicit step, with the application verifying rather than migrating. I had first recommended and the owner had first selected `pressly/goose` applying migrations at startup. The owner then raised that dbmate was already installed and asked which was actually better given these requirements.
The argument that decided it is least privilege. A binary that applies its own migrations needs a runtime role with DDL rights, which means the process serving requests can ALTER or DROP the tables holding sealed artifacts. For a system whose proposition is that its record lineage is immutable and attributable, that is the one place a structural guarantee would be replaced by trust — the same reasoning already enforced by "storage cannot lie about identity" rather than being relied on not to. Supporting reasons, in descending weight: a long migration or backfill does not belong in a starting process, where an advisory lock makes N−1 tasks wait and a slow index build can outlast a health-check grace period; migration and deploy stay separately reversible, so rolling a binary back does not leave the schema ahead of the code; plain SQL is reviewable by contributors who do not read Go.
The standard objection to a separate step — someone forgets it — is answered by the pattern already in use here: the binary refuses to start, exactly as an unreachable configured database already blocks startup rather than degrading to memory.
Slice 1 (migrations): complete. schema.sql deleted; its DDL is now `internal/adapters/postgres/migrations/20260819120000_plans_and_executions.sql`. `Open` verifies instead of applying. 53 store-check assertions pass, up from 48. `make verify` clean.
Slice 1 decision — dbmate is pinned in go.mod and invoked via `go tool`, not taken from the workstation. The README is explicit that pinned tools exist so workstation-global installations are not used, and CI already runs `make store-check`, so relying on a brew install would have made CI the exception and needed a setup step. Cost measured rather than assumed: dbmate bundles BigQuery (via gorm), ClickHouse, MySQL, and SQLite drivers, so pinning added ~850 lines to go.sum. `go list -deps ./cmd/maiden-lane` confirms ZERO of it reaches the application binary, and govulncheck stays clean, so the cost is noise in one file rather than shipped surface.
Slice 1 decision — the migration files are embedded to be READ, never applied. That is what makes the check precise: the binary knows exactly which versions it was compiled against and refuses a database missing any, instead of comparing against a version constant somebody must remember to bump. Verification needs only SELECT on `schema_migrations`, so it does not reintroduce the DDL privilege the design just removed. Versions are parsed from filenames rather than listed, so a migration cannot be added to the directory and forgotten in code.
Slice 1 decision — a database AHEAD of the binary is accepted, behind is refused. Old and new tasks run together during a rolling deploy, and refusing a forward schema would make every deploy a coordinated stop. Asserted in both directions.
Slice 1 decision — the initial migration keeps `IF NOT EXISTS` and says why in the file: it must adopt a database whose tables were created by the adapter's former implicit CREATE TABLE on open, so applying it there records the version and changes nothing. The same file states that later migrations must NOT do this, because once a database is under migration control a statement that silently does nothing hides a divergence rather than adopting one.
Slice 1 decision — `plan_storage_schema_out_of_date` is a distinct startup code from `plan_storage_unavailable`. Both block startup, but an operator told only "unavailable" would investigate networking and credentials for a database that answered perfectly well and had simply not been migrated. The error names the missing versions and the command to run, because "run migrations" is not actionable when the question is whether the deploy or the database is wrong.
Slice 1 tests: five new store-check assertions — versions derive from the embedded files and sort ascending; an unmigrated database is refused with an actionable message; a partially migrated one is refused naming the missing version; a database ahead of the build is accepted; and the initial migration is applicable twice, which is the same shape as adopting an existing database. The unmigrated cases need a scratch database created beside the test one, because store-check migrates the shared database before the tests run.
