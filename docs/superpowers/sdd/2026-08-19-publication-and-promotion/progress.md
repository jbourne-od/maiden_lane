The argument that decided it is least privilege. A binary that applies its own migrations needs a runtime role with DDL rights, which means the process serving requests can ALTER or DROP the tables holding sealed artifacts. For a system whose proposition is that its record lineage is immutable and attributable, that is the one place a structural guarantee would be replaced by trust — the same reasoning already enforced by "storage cannot lie about identity" rather than being relied on not to. Supporting reasons, in descending weight: a long migration or backfill does not belong in a starting process, where an advisory lock makes N−1 tasks wait and a slow index build can outlast a health-check grace period; migration and deploy stay separately reversible, so rolling a binary back does not leave the schema ahead of the code; plain SQL is reviewable by contributors who do not read Go.
The standard objection to a separate step — someone forgets it — is answered by the pattern already in use here: the binary refuses to start, exactly as an unreachable configured database already blocks startup rather than degrading to memory.

Slice 2 decision — RequiredProfileID rather than a profile key. A key is a name an author chose and can reuse; a ProfileID identifies one specific compiled contract. Binding the key would let the requirement change underneath a publication that had already been authorized by it.
Slice 2 decision — writing a policy is a compare-and-swap: the supplied version must be exactly one greater than the current one. The store does NOT allocate the next version. Two operators editing one target concurrently is the case this exists for, and for an audit-bearing rule, the loser learning it lost matters more than the convenience of not having to read first. Identical content under a recorded version succeeds so a retry is safe; different content under a recorded version is a conflict, because that is an attempt to rewrite what an existing publication pinned.
Slice 2 decision — version zero is refused rather than treated as absent, so "no policy" and "policy version zero" are not two states every reader must distinguish. Enforced in both adapters and by a CHECK constraint, so a direct SQL write cannot introduce what application code refuses.
Slice 2 Postgres implementation: the succession check and the insert are ONE statement, an INSERT ... SELECT whose WHERE compares the supplied version against `1 + COALESCE(max(version), 0)`. A source yielding no row inserts nothing, which expresses "your version does not follow the current one" without a transaction or a caller-held lock. The primary key handles the rest: a concurrent writer with the same version loses to a unique violation rather than overwriting, so immutability holds at the database and not only in application code. The concurrency assertion passing against a real database is what establishes that, and it also exercises the SQLSTATE match — a wrong code would surface a raw write error instead of ErrPolicyConflict and fail the assertion.

All four remaining clauses are establishable from the authenticated candidate, so the loose premise in #19 was never in the way of this slice.
Clause 1, static validation: established by a compiled Plan existing, not by re-running validation. Compile returns a Plan or a CompilationFailure and never both, and Plan has unexported fields with no exported constructor, so outside the kernel a plan with an identity is a plan the compiler accepted. Re-validating here would be a second implementation of the compiler's judgment, and a second implementation is a second answer.
Clause 2, provenance: a theorem, the same shape as clause 3's. Slice 6, rehydration: complete. This closes the #19 blocker. A stored execution can now be turned back into authenticated kernel artifacts, so the gate is reachable from a stored record and a rehydrated candidate satisfies every clause this build can answer.
THE DECISION, and the losing option lost on the project's own standard rather than on cost. Option (b) was a kernel verifier recomputing CheckpointArtifactID from stored components. It does not authenticate: it establishes that a stored tuple agrees with itself, and a wrong-but-self-consistent record is exactly what already does that. It fails the owner's correction from (b) — no projection may carry authorization weight — so it was never sufficient, independent of how cheap it was.
Option (a), re-execution, answers both halves at once: the artifacts are authenticated because this process's kernel just produced them, and the store is proven faithful because the products match what it recorded. Affordable because execution is deterministic by construction, which is the property the whole system rests on.
THE PRECEDENT WAS ALREADY IN THE CODEBASE, which is what made this a decision rather than an invention: PlanRecord's own documentation says an adapter "stores this input in its own encoding, recompiles on read, and requires the resulting PlanID to equal the one it stored". Re-derivation on read is the ratified pattern for plans. This extends it to executions. The worker already performs the same reconstruction from stored inputs, so nothing new was needed to run it.
Project moved from internal/worker to internal/app. Rehydration must compare a re-derived result against a stored one, and two implementations of the projection could disagree; a disagreement there is the worst kind, surfacing either as a false integrity failure on a faithful store or as a real divergence nobody noticed. One implementation makes the comparison exact by construction, and it belongs beside the SpineResult it projects.
Divergence names the field rather than returning a boolean. An integrity failure that says only "the store is wrong" sends someone to read everything; "the second checkpoint's canonical bytes" sends them to one row. The detail carries no value from either side, which matters more here than elsewhere: this error is produced while handling material that is already suspect, so including any of it would make a corrupt store a channel for whatever it contains. A test asserts neither the doctored nor the expected identity appears in the message.
Comparing CANONICAL BYTES is the check that earns the whole approach. Identities agreeing while the artifact they name differs is precisely the record no digest recomputation over stored fields would catch, and it is caught here.
New error class, IntegrityError with a closed IntegrityCode, distinct from InvalidInputError and InfrastructureUnavailableError because it is neither: the request was well formed and every dependency answered. What failed is the agreement between what a store recorded and what the kernel derives from inputs that same store holds. Two codes: REFERENCED_PLAN_ABSENT and STORED_RESULT_DIVERGED.
Divergence is an ERROR, not an outcome, while absent and pending are outcomes. A store the kernel cannot reproduce is a fault, and a caller must never be handed artifacts alongside a flag saying they might be wrong. Absent and pending are ordinary states, and pending keeps the lifecycle status so a caller can tell waiting from missing without a second read.
An execution naming an absent plan is an integrity failure rather than an absence: execution identity is derived from the plan, so the plan is not recoverable from the execution, and the store is failing to answer for what it holds.
Publishable takes the profile as a parameter rather than returning a list of assessments to choose from. A caller selecting an assessment could select the one that answers most favourably; the readiness clause asks about the profile the target requires, so that is the only correct selector.
EXHAUSTIVENESS GUARD, and it found two real problems in itself. The divergence comparison is hand-written so it can diagnose, which reflect.DeepEqual cannot; the hazard is a forgotten field in which storage may diverge undetected while nothing looks wrong. A reflective test walks every field of every nested struct and requires each to be caught. Verified by deleting one comparison: it fails by name.
Problem one in the guard: it SKIPPED fields it could not alter, and a skipped field is an uncovered field hidden behind a green run. Truncating a slice cannot alter an empty one, so whichever fields happened to be empty in the fixture were silently uncovered. Fixed by appending instead of truncating, which alters empty and full slices alike, and by making an unalterable field a failure rather than a skip.
Problem two was in my own hand-written mutation list: the "missing requirement removed" case doctored assessment 0, which is already ready with none, so it altered nothing. The test failed for the right reason — rehydration correctly found nothing wrong — and now targets the assessment that actually carries them.

Slice 7, the publication HTTP surface: complete. POST /v1/publications and GET /v1/publications/{customerID}/{target}. Everything built in slices 4 through 6 had no caller outside the process; this completes the vertical.
FOLLOWED THE SPEC RATHER THAN INVENTING: §16 already names both endpoints, and its behavioural rule already said publication "requires the expected current target version" — the same line that caught blocker 1 in the #22 review. The request shape comes from that rule: a target, a sealed checkpoint, a passing assessment, gate evidence, and the expected version.
THE CENTRAL CONTRACT DECISION: a gate refusal is 200, not an RFC 9457 problem. §16 already ratifies the principle for readiness — "needs_input is a successful assessment response, not a problem" — and a promotion refusal is the same kind of thing: the computation produced a real answer. An operator told only "refused" cannot act, while the clause list says which requirement failed and whether the answer was fail or not_evaluated. 201 when the pointer advanced, 200 when refused or unchanged, 409 for a stale expected version, 500 for a store the kernel cannot reproduce.
The request names IDENTITIES and the service re-derives the evidence. That is not a convenience: authorization rests on artifacts the kernel produced, which cannot be transmitted or rebuilt from bytes, so a client able to supply evidence would be supplying something nothing verified. The handler rehydrates, then resolves the named checkpoint and assessment AGAINST what re-execution produced rather than trusting them as descriptions of it. A checkpoint the execution did not produce, or an assessment not taken against it, is simply absent.
A client cannot shop for a favourable answer. It names an assessment; the service establishes that assessment was really taken against this checkpoint and uses ITS profile to select the evidence. Naming a profile directly would let a caller pick the profile its checkpoint happens to satisfy.
An unconfigured target is a refusal, not a 404. Reporting absence would make a configuration gap look like a missing artifact. Likewise a target never published to reads as 200 with status unpublished, while a specific version that does not exist IS a 404 — the first is the ordinary initial state of every target, the second is a real absence.
PublicationStatus is derived on read, not stored, exactly as the port promised: the highest version is published, every lower one superseded. A test asserts a superseded version stays readable, which is what keeps an old decision explainable.
The wire clause vocabulary is an explicit table rather than a string conversion of the domain constants. The two are independently ratified — the wire enum is a published contract and the domain constants are not — so letting one render the other would make a rename in either a silent breaking change in the other. A clause with no wire name is omitted rather than guessed at, which makes the clause list short and fails the contract's minItems of 9: a detectable violation beats a fabricated vocabulary word. A test enumerates all nine.
Policies and Publications are OPTIONAL dependencies. A deployment without a control plane serves the semantic surface and reports these routes as 503, rather than panicking or — worse — refusing, which would claim the gate had been evaluated.
Verified against a running server, not only in tests: with no policy configured, all nine clauses come back not_evaluated / information_absent, because the missing information is the policy.
GAP RECORDED RATHER THAN PAPERED OVER: a target policy has NO HTTP surface, in §16 or in the contract. Policies are control-plane configuration and operator-managed, so publication cannot be driven end to end over HTTP by an operator today; the six-clause pass is verified through the real router in tests, where the policy is seeded directly. Adding an endpoint §16 does not have would be inventing surface. This is the next gap, not a defect in this slice.
Also still open: the demo UI does not show the gate. It could now, which it could not before this slice.
