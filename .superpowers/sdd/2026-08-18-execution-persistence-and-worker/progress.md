# SDD ledger — plan: docs/superpowers/plans/2026-08-18-execution-persistence-and-worker.md
Setup: branch `claude/execution-persistence` off `main` at da902b9 (PR #10 merged); baseline `make verify` passed.
Owner decision ratified 2026-08-18: POST /v1/executions returns 202 ONLY. One execution path and one lifecycle; a caller wanting a result polls the read endpoint, and a convenience wrapper belongs in a client rather than a second server mode. This fully retires the interim synchronous deviation rather than preserving it beside its replacement. It is a breaking contract change, acceptable now because no deployment exists and no client depends on the synchronous shape — and precisely because that will stop being true, which is an argument for doing it now rather than later.
Three properties this slice gets from the kernel's determinism rather than building, each to be asserted rather than assumed: (1) submission is idempotent by construction because ExecutionID is derived from the semantic request, so no idempotency key, deduplication store, or expiry policy is needed; (2) at-least-once delivery is sufficient because re-running a reclaimed execution produces byte-identical artifacts, so no fencing tokens and no exactly-once protocol are needed and duplicate execution can only waste CPU; (3) no transactional outbox is required, because the HLD's outbox exists to reconcile a dual write to AWS Batch, and a worker polling the same PostgreSQL that holds the work has no second system — the outbox arrives when Batch does.
Consequence of the 202 switch, identified during planning: with in-memory storage a separate worker process cannot see the queue, so an enqueued execution would never run and every read would report pending forever, making the default configuration silently useless. Therefore `serve` runs an in-process worker by default with `--no-worker` for the split deployment shape. The API still answers 202 immediately either way, so the worker is never in the response path — which is what distinguishes this from the rejected `Prefer: wait` option, where API behaviour would have depended on worker availability.
Task 1: complete. ports.ExecutionStore declared with Enqueue (idempotent, reporting created-versus-found), Claim (lease-based, the one method that necessarily selects across tenants because a worker serves all of them and therefore must never be reachable from a request path), Complete, Fail, and a tenant-scoped Get. ExecutionRecord distinguishes a pending execution (no result) from a completed one, so a caller cannot infer a result from a status. Fresh `make verify` passed.
Task 1 storage-shape decisions: (1) the result is a PROJECTION — identities, digests, closed codes — because Journal, State, and Assessment are kernel values that cannot be reconstructed from bytes, and a caller needing one re-executes, which is deterministic. (2) Sealed checkpoint and assessment CANONICAL BYTES are retained alongside their identities, justified rather than speculative: sealing produces an artifact, and storing only its digest keeps the receipt while discarding the goods; a later publication step must expose an artifact that was already validated rather than re-derive one. The bytes are opaque to storage — comparable without being decodable, which is exactly what replay verification needs and all it needs. (3) StoredFailure carries only a closed kind and code; a rejection's canonical detail lives in the semantic artifacts, so everything stored here is safe to render to a caller.
Task 1 contract: nine assertions, weighted toward queue semantics because that is where the risk is — a store that looks correct single-threaded can still hand one execution to two workers, strand work when a worker dies, or return a leased execution to a second claimer. Includes idempotent enqueue on the derived identity, no double-claim while leased, reclaim after lease expiry with the reclaimed request byte-identical to the original, never claiming a completed execution, exact round-trip of sealed bytes, pending-carries-no-result, bounded operational failure reasons, tenant isolation with a foreign execution indistinguishable from an absent one, cancellation, and the central one: six concurrent claimers over twenty-four executions must partition them exactly, nothing claimed twice and nothing left behind.
Task 1 fixture decision: ExecutionRequestFixture derives its identities through a real semantic.BindRun rather than fabricating them. That matters specifically for a queue contract — identities derived from the input are what make enqueueing idempotent, so a fixture with invented identities would let a store pass the idempotence assertion while the property failed for real requests.
Task 1 deliberate sequencing: the contract cannot run yet because no adapter implements ExecutionStore. That is the intended RED for Task 2 rather than an omission. One assertion is also deferred on purpose — that a stored artifact whose bytes do not match its digest fails closed — because verifying that requires the kernel to expose digest verification (the kernel owns hashing, so it must own verification), and adding it in Task 3 lets both adapters implement it once rather than retrofitting the contract afterwards.

Task 3: complete. internal/adapters/postgres now implements ports.ExecutionStore. Task 3 claim implementation: one statement, an UPDATE whose subquery selects with FOR UPDATE SKIP LOCKED and LIMIT 1. SKIP LOCKED is what makes several workers safe against one queue — a worker steps over rows another is already claiming rather than blocking, so the queue partitions instead of serializing. Doing the select and the claim in one statement means no window exists in which a row is selected but not yet claimed. A partial index over unfinished rows keeps claiming from slowing as processed history accumulates.
Task 3 KERNEL ADDITION AVOIDED — correcting what I flagged earlier. I had said Task 3 would need a small kernel addition exposing digest verification so both adapters could prove a stored artifact's bytes match its digest. It turned out unnecessary and the alternative is better. Verifying a semantic digest would have required the adapter to learn how the kernel derives identity, which is precisely what must not happen. Instead the adapter computes ITS OWN content hash over ITS OWN encoding and verifies that on read. The guarantee is narrower and the difference is documented in code: it proves storage returned the bytes it was given, NOT that those bytes were correct. That is the property storage actually owes, and unlike plans a sealed artifact cannot be re-derived cheaply because reproducing it means re-executing. No kernel change was made in this slice.
Task 3 CONTRACT HOLE found and closed: the reclaim assertion compared the state digest of two successive claims against each other, so a lossy encoding would have corrupted both identically and still passed. Added "returns a claimed input identical to the enqueued one", which compares against the request as submitted, before it ever reached storage — the execution equivalent of the plan store's round-trip assertion. Every downstream identity derives from that state digest, so a lossy round trip would have executed something other than what was accepted. It passes on both adapters, which is what actually establishes the codec is lossless.
Task 3 codec decisions: the stored request is self-describing, carrying the schema declarations alongside the pinned state, so a claim is a complete unit of work rather than a pointer into other state that may have moved; the alternative would have made ExecutionStore.Claim unable to return a fully-formed request without consulting the plans table. Entity identities and the lineage identity are stored whole rather than re-derived from source keys and namespaces, because the identity is what the run was bound to and re-deriving risks producing a different one and silently executing a different input. Value kind is stored beside the payload so a string and an atom holding identical bytes stay distinguishable, as they must, being different values with different identities.

Review finding 1 and 2 (medium) — ACCEPTED, and they falsify reasoning repeated across three commit messages. I argued at-least-once delivery is safe because a second attempt reproduces byte-identical artifacts. That covers a duplicate Complete; it does NOT cover a late Fail from a worker whose lease expired arriving after another worker succeeded, which silently destroyed the true outcome and left status=failed beside a SpineStatus=succeeded result. Complete was equally unguarded and wrote result.Status through unvalidated, so a non-terminal status produced a row that still matched the claim predicate with a null lease — an execution re-run forever, while Get reported the pending-with-result shape ExecutionRecord documents as impossible. The property was real but narrower than claimed. Both transitions are now one-way and guarded in SQL and in memory, Fail clears any recorded result, Complete clears any stale failure reason, and non-terminal statuses are refused. Review finding 3 (medium) — ACCEPTED, and the sharpest. The plan's own global constraint says identities are re-derived and compared, never read and trusted. For plans that holds; for executions the identity columns sat OUTSIDE the content hash, so an UPDATE altering execution_id or run_id left both hashes valid and a worker would execute a request bound to an identity the kernel never derived. Fixed at the storage layer by hashing the identity columns together with the request blob. The full semantic check belongs in the worker, which has the plan and can re-derive ExecutionID via BindRun — recorded as a required step of Task 4, not deferred vaguely. TestTamperedIdentityColumnsFailClosed covers run_id, plan_id, and format.
Review finding 4 (medium) — ACCEPTED. The executions table had no format column while plans did. This codec persists raw enum ordinals, so a renumbered ValueKind or ProvenancePolicy would decode old rows into DIFFERENT values with a still-valid content hash, and unlike a plan an execution is not recompiled on read, so nothing would catch it. Added format with refusal of unknown versions.
Review finding 5 (low) — ACCEPTED. The claim UPDATE commits before the hash and decode checks, so a poisoned row was marked running with a fresh lease and re-selected every lease interval forever, since ORDER BY enqueued_at makes it the first candidate again. Task 4 closes the semantic half of review finding 3. verifyIdentity re-derives the execution and run identities through a real semantic.BindRun against the fetched plan and refuses when either differs from the identity the execution was claimed under. This is where the constraint that identities are re-derived rather than read and trusted is actually honoured for executions: the store cannot do it, because an ExecutionID comes from binding a run against a plan and the store has only a PlanID, while the worker has both. TestWorkerRefusesAnExecutionWhoseIdentityDoesNotReproduce enqueues the genuine input under a plausible but wrong execution identity and requires a terminal identity_mismatch with no semantic result — the tampering path the storage-layer hash alone could not cover.
Task 4 inability classification, refined beyond the plan's wording: the plan said machinery inability should leave an execution claimable. That is right only for causes where repetition can plausibly change the outcome. Cancellation and infrastructure unavailability leave it claimable so an expired lease brings it back; a typed InvalidInputError and any internal inconsistency are TERMINAL, because leaving a deterministic failure claimable would spin forever on an input that cannot succeed. Both directions are asserted.
Task 4 panic decision: a panic is contained, logged with a bounded code, and recorded as a terminal internal_error. Retrying was rejected because execution is deterministic — a second attempt on identical input panics identically — so leaving it claimable would spin. The recovered value is deliberately discarded rather than stored, since it can carry payload; a test asserts the panic value does not reach the record.
Task 4 known limitation recorded rather than discovered later: because Enqueue is idempotent on a derived identity, a terminally failed execution CANNOT be retried by resubmitting — the same request returns the existing failed row. Marking an execution failed is therefore permanent for that input. That is correct for genuinely deterministic failures, which is why the classification above matters so much, but it means a future slice needs an explicit retry or reset operation for cases a later build could handle differently.
Task 4 reclaim proof: TestReclaimedExecutionProducesIdenticalArtifacts runs the same request through two independent queues and requires the final state digest, journal prefix digest, every checkpoint artifact identity and byte sequence, and every assessment identity to match. This is the assertion that makes at-least-once delivery defensible; without it the queue would need exactly-once machinery to be correct.
