# SDD ledger — plan: docs/superpowers/plans/2026-08-18-execution-persistence-and-worker.md
Setup: branch `claude/execution-persistence` off `main` at da902b9 (PR #10 merged); baseline `make verify` passed.
Owner decision ratified 2026-08-18: POST /v1/executions returns 202 ONLY. One execution path and one lifecycle; a caller wanting a result polls the read endpoint, and a convenience wrapper belongs in a client rather than a second server mode. This fully retires the interim synchronous deviation rather than preserving it beside its replacement. It is a breaking contract change, acceptable now because no deployment exists and no client depends on the synchronous shape — and precisely because that will stop being true, which is an argument for doing it now rather than later.
Three properties this slice gets from the kernel's determinism rather than building, each to be asserted rather than assumed: (1) submission is idempotent by construction because ExecutionID is derived from the semantic request, so no idempotency key, deduplication store, or expiry policy is needed; (2) at-least-once delivery is sufficient because re-running a reclaimed execution produces byte-identical artifacts, so no fencing tokens and no exactly-once protocol are needed and duplicate execution can only waste CPU; (3) no transactional outbox is required, because the HLD's outbox exists to reconcile a dual write to AWS Batch, and a worker polling the same PostgreSQL that holds the work has no second system — the outbox arrives when Batch does.
Consequence of the 202 switch, identified during planning: with in-memory storage a separate worker process cannot see the queue, so an enqueued execution would never run and every read would report pending forever, making the default configuration silently useless. Therefore `serve` runs an in-process worker by default with `--no-worker` for the split deployment shape. The API still answers 202 immediately either way, so the worker is never in the response path — which is what distinguishes this from the rejected `Prefer: wait` option, where API behaviour would have depended on worker availability.
Task 1: complete. ports.ExecutionStore declared with Enqueue (idempotent, reporting created-versus-found), Claim (lease-based, the one method that necessarily selects across tenants because a worker serves all of them and therefore must never be reachable from a request path), Complete, Fail, and a tenant-scoped Get. ExecutionRecord distinguishes a pending execution (no result) from a completed one, so a caller cannot infer a result from a status. Fresh `make verify` passed.
Task 1 storage-shape decisions: (1) the result is a PROJECTION — identities, digests, closed codes — because Journal, State, and Assessment are kernel values that cannot be reconstructed from bytes, and a caller needing one re-executes, which is deterministic. (2) Sealed checkpoint and assessment CANONICAL BYTES are retained alongside their identities, justified rather than speculative: sealing produces an artifact, and storing only its digest keeps the receipt while discarding the goods; a later publication step must expose an artifact that was already validated rather than re-derive one. The bytes are opaque to storage — comparable without being decodable, which is exactly what replay verification needs and all it needs. (3) StoredFailure carries only a closed kind and code; a rejection's canonical detail lives in the semantic artifacts, so everything stored here is safe to render to a caller.
Task 1 contract: nine assertions, weighted toward queue semantics because that is where the risk is — a store that looks correct single-threaded can still hand one execution to two workers, strand work when a worker dies, or return a leased execution to a second claimer. Includes idempotent enqueue on the derived identity, no double-claim while leased, reclaim after lease expiry with the reclaimed request byte-identical to the original, never claiming a completed execution, exact round-trip of sealed bytes, pending-carries-no-result, bounded operational failure reasons, tenant isolation with a foreign execution indistinguishable from an absent one, cancellation, and the central one: six concurrent claimers over twenty-four executions must partition them exactly, nothing claimed twice and nothing left behind.
Task 1 fixture decision: ExecutionRequestFixture derives its identities through a real semantic.BindRun rather than fabricating them. That matters specifically for a queue contract — identities derived from the input are what make enqueueing idempotent, so a fixture with invented identities would let a store pass the idempotence assertion while the property failed for real requests.
Task 1 deliberate sequencing: the contract cannot run yet because no adapter implements ExecutionStore. That is the intended RED for Task 2 rather than an omission. One assertion is also deferred on purpose — that a stored artifact whose bytes do not match its digest fails closed — because verifying that requires the kernel to expose digest verification (the kernel owns hashing, so it must own verification), and adding it in Task 3 lets both adapters implement it once rather than retrofitting the contract afterwards.
Task 2: complete. The in-memory Store now implements ports.ExecutionStore alongside PlanStore and passes all eleven execution contract assertions, including the concurrent-partition one. Race detector clean; fresh `make verify` passed.
Task 2 decisions: claim order is kept in an explicit insertion-ordered slice rather than relying on Go map iteration, so claiming is predictable instead of arbitrary — the same habit the kernel requires for semantic ordering, applied here even though this is operational. Lease expiry is the only place this adapter observes wall-clock time, and it is confined to operational state that never reaches the kernel: nothing about when an execution ran may influence what it computed. Results are deep-copied on the way in AND on the way out, because the sealed bytes ARE the artifact and a caller able to mutate them would corrupt every later reader's view of something meant to be immutable.
Task 2 documented limitation, asserted rather than described: TestQueueIsNotVisibleToAnotherProcess proves a second store cannot see the first's queue. That is the concrete consequence of the 202 switch identified during planning, and it is why serve must run an in-process worker when storage is in memory.
Task 2 CONTRACT DEFECT found by probing and fixed: the concurrent-claimers assertion looped until the queue drained, so an adapter that hands out work without recording the claim returned found=true forever and HUNG the test. In CI that is a ten-minute timeout with no useful message rather than a failure naming the defect. The loop is now bounded at twice the number of executions, and exceeding the amount of work that exists is itself the assertion. Re-probed: a deliberately leaky queue that never marks work claimed now fails in 0.05s naming six specific defects, including "a leased execution was claimed twice". Worth noting the first probe attempt produced no output at all, which is what exposed the hang — a contract suite that hangs on a broken implementation is barely better than one with no teeth.
