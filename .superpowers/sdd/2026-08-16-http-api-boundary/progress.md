Cause: semantic.Plan exposes only SchemaDigest(), not the Schema, but binding a later run needs the Schema itself to construct the initial state. Task 3 decisions: PutPlan is idempotent rather than conflict-checking, because plan identity is content derived and the same identity always denotes the same plan. GetPlan reports another tenant's artifact as absent with a nil error, never as a distinct error, since distinguishing the two leaks existence. The store honors context cancellation even though an in-memory map cannot block, so the port behaves like the durable adapter that will replace it. No defensive deep copy is made on read and the reason is recorded in code: Schema and Compilation are kernel values whose getters clone, which the immutability test proves by mutating returned transformations, checkpoints, and canonical bytes and re-reading.

Task 2 decisions: (1) compiler diagnostic codes are re-declared in httpapi rather than imported from semantic, so widening the compiler's vocabulary cannot widen the published wire contract without a deliberate edit at the boundary; unratified codes are dropped rather than published. Hostile tenant cases under test include CRLF injection, null bytes, a Cyrillic homoglyph, path traversal, SQL-ish text, and an over-length value.

Task 4 owner decisions ratified 2026-08-16: (1) unknown JSON members are REJECTED, not ignored. Rationale recorded in code: a misspelled member would otherwise be silently dropped and the run would proceed over inputs the client did not intend, producing a valid artifact that is quietly wrong. The tradeoff is stated beside it — new optional members must reach the contract before any client may send them. (2) GET /v1/plans echoes the declarations; POST does not. The deciding argument was that the trace allowlist is three identities plus closed tokens and metrics are bounded enums, so operational telemetry is STRUCTURALLY incapable of ever carrying declarations; an operator landing on a PlanID from a trace has no other way to ask what the plan says. Crucially the projection is derived from the compiled plan via CompiledTransformation.Declaration(), not from a stored copy of the request, so it shows what the compiler accepted in canonical order — where that differs from what was sent, the difference is the canonicalization, which is usually the thing being looked for.
Task 4 load-bearing proof: TestStateFromWireMatchesTheKernelConstructedDigest asserts a state built from JSON has a StateDigest byte-identical to the same state built directly through the kernel. Every downstream identity derives from that digest, so a divergence would silently fork the whole artifact graph. TestWireOrderingDoesNotChangeIdentity proves JSON array order is not semantic. TestPlanProjectionRoundTripsThroughTheCompiler re-translates the projected declarations and recompiles them, requiring the identical PlanID: a projection that did not round-trip would be describing a plan that does not exist. TestPackageNeverConstructsADigest scans this package's production source and fails on a `"sha256:` literal or a crypto/sha256 import, so identities can only be projected, never assembled.
Task 4 decisions: entity identities are derived from lineage plus canonical source key rather than accepted from clients, so a client cannot forge or collide one; proved by showing a lineage change invalidates every prior identity. An absent world becomes the real versioned empty world rather than a zero value, since the empty world participates in run identity. Unknown value kinds, kind/payload disagreement, multiple payloads, unratified world reference kinds, invalid executor identities, and unratified provenance policies are all refused rather than coerced.
Task 4 generator change: always-prefix-enum-values was enabled in both codegen configs. Without it the contract's value kinds generated as bare `String`, `Int64`, and `Atom`, polluting the package namespace and guaranteed to collide once a second enum reuses a value name such as `Ready`. Contract and generated code reverified in sync.
Task 4 documented limitation (recorded, not hidden): encoding/json matches member names case-insensitively, so DisallowUnknownFields does NOT reject `rootkey` for `rootKey`. A first test asserted it would; the assertion was wrong about Go, not about the code. The member still maps to the field the client intended, so no data is dropped and no artifact is silently wrong, which is the risk strict decoding exists to prevent. What it does mean is that this server accepts casings the contract does not declare, and clients must not depend on them. TestStrictDecodingIsCaseInsensitiveForKnownMembers records the behavior explicitly so the gap is known rather than discovered later; closing it would require decoding into raw members and comparing keys exactly, which is not worth the reflection cost for a mismatch that preserves intent.
